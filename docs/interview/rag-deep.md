# 面试题深度：RAG 专题

## 题目 1：设计一个企业级 RAG 系统

### 考察点
- 系统架构设计能力
- 对 RAG 全链路的理解
- Trade-off 思维
- 扩展性 & 容灾意识

### 答题框架
```
1. 需求澄清（30秒）
2. 高层架构图
3. 核心模块详解
4. 数据库 Schema
5. API 设计
6. Trade-off 讨论
7. 扩展性 & 容灾
8. 高频追问
```

### 标准答案

#### 1. 需求澄清
- **功能**：文档上传、语义问答、引用溯源、多轮对话
- **非功能**：响应 < 2s，Recall@5 > 85%，可用性 99.9%
- **规模**：10 万文档，1000 DAU，日均 1 万查询

#### 2. 架构
```
用户 → Gateway → Query 理解 → 检索 → 重排序 → 生成 → 输出
                                    ↓
                              向量数据库
```

#### 3. 核心模块

**文档处理**：
- 解析：PDF（Nougat）、HTML（BeautifulSoup）、表格（TATR）
- 分块：递归分块 512 tokens + 50 overlap
- 元数据：来源、时间、章节

**检索**：
- Embedding：BGE-large-zh-v1.5
- 混合检索：BM25 + 向量 → RRF 融合
- 向量数据库：Milvus

**重排序**：
- Cross-Encoder：BGE-Reranker-v2-m3
- 检索 Top-50 → Rerank → Top-5

**生成**：
- Prompt：Context + Question + 约束
- 引用：标注答案来源
- 拒答：无相关信息时诚实拒绝

#### 4. Trade-off

| 决策 | 选项 A | 选项 B | 选择 | 原因 |
|------|--------|--------|------|------|
| 分块大小 | 256 | 1024 | 512 | 平衡精度和上下文 |
| 检索方式 | 纯向量 | 混合 | 混合 | 关键词+语义互补 |
| 重排序 | 无 | 有 | 有 | 精度提升 10-15% |

#### 5. 扩展性
- 文档量增长：Milvus 水平扩展
- 查询量增长：Gateway + 检索节点水平扩展
- 多区域：就近部署 + 数据同步

### 常见坑 & 避坑

| 坑 | 后果 | 避坑 |
|----|------|------|
| 分块太大 | 噪声多，精度低 | 512 tokens + 重叠 |
| 纯向量检索 | 关键词匹配差 | 加入 BM25 |
| 无重排序 | 相关性差 | Cross-Encoder |
| 无拒答机制 | 幻觉 | 置信度阈值 + 拒答 |
| 无引用溯源 | 无法验证 | 标注来源 |

### 追问链

**追问 1：分块大小如何选择？**
- 太小：上下文不完整
- 太大：噪声多
- 建议：512 tokens，overlap 50-100
- 实验：对比 256/512/1024 的 Recall@K

**追问 2：如何评估 RAG 质量？**
- 检索：Recall@K、MRR
- 生成：Faithfulness、Relevancy
- 端到端：RAGAS 四指标
- 在线：用户反馈、A/B 测试

**追问 3：RAG 中幻觉如何抑制？**
- 提高检索质量
- Prompt 约束："仅基于给定信息"
- 引用溯源
- 输出审核（LLM-as-Judge）

**追问 4：如何处理多轮对话？**
- 会话管理：滑动窗口 + 摘要压缩
- Query 改写：将指代消解为完整 Query
- 上下文注入：历史对话作为额外 Context

**追问 5：向量数据库如何选型？**
- Milvus：十亿级，分布式
- Qdrant：亿级，轻量
- Pinecone：全托管，快速验证

| 等级 | 标准 |

| 优秀 | 完整架构 + Trade-off + 追问对答如流 |
